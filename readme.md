**실제 스펙과 다른 지점들**

실제 발행 엔드포인트는 `https://xapi.bolta.io/v1/taxInvoices/issue`이고 인증은 API 키 Basic 인증인데, 코드는 `api.bolta.io/v1`에 fetch 자체를 안 합니다. 요청 스키마도 전혀 달라요 — 실제로는 `supplier`/`supplied`에 `identificationNumber`, `organizationName`, `representativeName`, 품목에 `supplyCost`/`tax`를 쓰고, `purpose`(영수/청구) 필드가 필수인데 지금 타입엔 `regNo`/`buyer`/`supplyAmount`로 되어 있고 영수·청구 구분은 아예 없습니다. 제일 중요한 차이는 아키텍처인데, 실제 발행은 `issuanceKey`만 즉시 반환하는 비동기 방식이고 발행 완료는 웹훅으로 통보받거나 조회 API로 확인합니다. 목처럼 동기로 승인번호가 바로 오는 구조가 아니라서, 서브도메인2 백엔드에 웹훅 수신 엔드포인트 + 상태 머신이 필요해요. 수정발행도 사유별로 엔드포인트가 나뉘고, 계약 해제는 작성일자만 전달하며 원본 품목이 음수면 수정발행 불가, 이중발급은 요청 본문 없이 호출하는 식이라 지금의 `AmendmentReasonCode '1'~'6'` 단일 필드 설계와 안 맞습니다.

**공동인증서 — 맞는데, 개발은 지금 시작할 수 있어요**

알고 계신 게 맞습니다. 실제 플로우는 회원가입·워크스페이스 생성 → 테스트 API 키 발급 → 발급자 등록(`issuerId` 획득) → 인증서 등록 URL을 API로 받아 공동인증서 등록 순서예요(지금 코드엔 이 "발급자" 개념 자체가 없습니다). 다만 좋은 소식은, 테스트 환경에서는 테스트 인증서를 제공해서 실제 공동인증서 없이도 연동 테스트가 가능하고, `test_` 키로는 포인트 충전 없이 무료로 모든 발행 요청이 가상 처리된다는 점입니다. 라이브 키는 사전 포인트 충전이 필요하고요. 즉 공식 신청·인증서는 라이브 전환 시점의 문제이고, 회원가입만 하면 지금 바로 실스펙 개발이 가능합니다.
