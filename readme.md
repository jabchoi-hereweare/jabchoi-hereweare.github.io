# 세금계산서 모듈 리뷰 & 아키텍처 검토

> 대상: `jabchoi-hereweare.github.io` (회무사 1회 — 세금계산서 데모 + `modules/tax-invoice` 이식용 모듈)
> 목적: 기존 ERP(React / Next.js / TypeScript / Tailwind, MySQL, Zustand, Docker)에 세금계산서 기능을 통합하기 위한 사전 검토
> 작성일: 2026-08-11

## 1. 코드 리뷰

### 1-1. 전체 평가

프로젝트는 회무사 데모 셸(페이지 11개)과 `src/modules/tax-invoice`(타입 · 검증 · 계산 · 헤드리스 훅 · API 클라이언트)로 구성되며, 총 약 8,000줄이다. 핵심 자산은 데모 셸이 아니라 모듈 폴더다.

가장 잘된 부분은 **모듈 경계 설계**다. `utils`(MOD-10 검증, 세액 계산, 발급기한, 이상탐지)가 전부 React 의존성 없는 순수 함수라서, ERP의 Next.js 서버(API Route)에서 그대로 재사용할 수 있다. 프런트의 실시간 검증과 서버 저장 직전 검증을 같은 함수로 이중 실행할 수 있다는 뜻이다. `useTaxInvoiceForm`을 헤드리스 훅으로 분리한 것도 좋다 — 데모 UI를 버리고 ERP 그리드에 붙일 때 훅만 가져가면 된다. 5대 날짜 스키마(`writeDate` / `issuedAt` / `transmittedAt` / `statutorySupplyDate` / `revenueRecognizedAt`)를 타입으로 분리해 이상탐지 룰의 입력으로 삼은 구조는 이 프로젝트의 핵심 자산이며, MySQL 테이블 설계로 거의 그대로 옮길 수 있다.

MOD-10 구현은 9번째 자리를 `floor(step9/10) + step9%10`으로 처리하는데, 표준 구현(`d9*5 + floor(d9*5/10)`)과 형태는 달라도 mod 10 기준으로 수학적으로 동치이므로 결과는 정확하다.

### 1-2. 수정 필요 — 로직 버그 3건

**① 지연전송 판정이 시각 차 24시간 기준 (`anomalyDetector.ts` 룰 3)**
현재 `transmitTime - issueTime > oneDayMs`로 판정하지만, 법적 기준은 "발급일의 **다음 날까지** 전송"이므로 날짜 단위로 비교해야 한다. 지금 로직이면 23:00 발급 → 다음 날 23:30 전송(적법)이 24.5시간 차이로 오탐되고, 23:50 발급 → 다음다음 날 00:30 전송 케이스 판정도 어긋난다.
→ **수정**: `issuedAt`의 날짜 + 1일 < `transmittedAt`의 날짜 로 변경.

**② 과세기간 이월 판정이 연도를 무시 (룰 1)**
`(writeMonth <= 6 && supplyMonth >= 7)` 방식으로 월만 비교한다. 2025-12 공급분을 2026-07에 작성한 극단 케이스가 CRITICAL로 잡히지 않고, 같은 월이면 연도가 달라도 통과한다.
→ **수정**: `YYYY-반기` 키(예: `2026-1H`)를 만들어 비교.

**③ 세액 절사에 `Math.floor` 사용 (`taxCalculators.ts`)**
수정세금계산서는 음수 금액이 들어가는데 `Math.floor(-100.5) = -101`이라 음수에서 절사 방향이 반대가 된다. 사유코드 3(환입) · 4(계약해제) 케이스에서 세액이 틀어진다.
→ **수정**: `Math.trunc` 또는 부호 분리 처리.

### 1-3. 개선 권장

- **발급기한 공휴일 연장 미처리**: 익월 10일이 토·공휴일이면 다음 영업일로 연장되는 규정이 빠져 있다. 데모에선 무방하나 ERP 반영 시 공휴일 테이블이 필요하다.
- **기본 샘플 데이터가 MOD-10 불통과**: `123-45-67890`, `987-65-43210` 모두 체크섬 실패라 첫 화면부터 경고가 뜬다. "초록불 4개" 데모 취지에 맞게 체크섬 통과하는 가짜 번호로 교체(가중치 역산으로 생성 가능).
- **API 키의 프런트 노출 구조**: `BoltaTaxInvoiceApiClient`가 프런트에서 apiKey를 들고 직접 발행하는 모양새다. 실제 연동 시 발행은 반드시 백엔드에서 수행하고 프런트는 자체 백엔드만 호출해야 한다. 발행은 가산세가 걸린 비가역 행위이므로 **멱등키(idempotency key) + 발행 이력 테이블(요청·응답 원문 저장)** 설계가 필요하다. `issuedAt` / `transmittedAt`은 응답에서 채워지므로 이 테이블이 자연스러운 소스가 된다.
- **폼 상태와 도메인 타입 혼재**: `quantity: number | ''` 같은 입력폼 상태가 도메인 타입에 섞여 있다. 폼 상태 타입과 저장용 도메인 타입을 분리하면 MySQL 스키마 매핑이 깔끔해진다.
- **Zustand 통합 방침**: 훅 내부 `useState`를 전역으로 옮기지 말 것. 폼 하나의 상태는 지역 상태가 맞다. "발급 전 문서함" 같은 목록·상태만 Zustand로 올린다.
- **저장소 위생**: `dist/`가 커밋되어 있고 해시가 다른 빌드 산출물(js 5개, css 4개)이 누적되어 있다. CI 배포 시 `dist`는 gitignore. 루트에 떠 있는 `deploy.yml`은 워크플로 폴더로 정리. `readme.md`("chk this out" 한 줄)는 `hoemusa_ep01_plan_and_implementation.md`를 승격해 대체.
- **순수 CSR**: 서버 렌더링이 없어 크롤러가 본문을 못 읽는다. 콘텐츠 노출이 목적이면 프리렌더링 고려.
- **세법 수치 검증**: 가산세율(지연발급 1%, 지연전송 0.3%), 익월 10일 기한, 부가법 §39·§17 인용이 하드코딩되어 있다. 프로덕션 반영 전 법제처 원문으로 교차검증할 것(korean-law 커넥터의 `verify_citations` 활용). 세율·가산세율을 1층 "Rule"로 하드코딩하는 설계 자체는 유효하나, 개정 대응을 위해 **상수 파일 하나로 집약** 권장.

## 2. 아키텍처: 서브도메인2 분리 + DB 공유

### 2-1. 결론

3인 분업(ERP / 자동화 / 세금계산서) + 발행이라는 비가역 도메인 조건에서 **서브도메인2 분리는 정석에 가까운 선택**이다. 세금계산서는 발행 순간 가산세가 걸리므로, ERP 본체 배포에 묶여 같이 롤백되거나 타인 커밋에 영향받는 구조가 가장 위험하다. 분리하면 배포 주기 · 장애 범위 · 책임 소재가 개발자 단위로 나뉘고, Docker 환경이 정착돼 있으므로 컨테이너 1개 + 리버스 프록시 라우팅 추가로 끝난다.

### 2-2. 조건 — "공유 DB의 함정" 차단 규칙 3가지

두 앱이 같은 테이블을 자유롭게 읽고 쓰는 공유 DB 통합은 시간이 지나면 반드시 깨진다(ERP 쪽 컬럼 변경 → 세금계산서 앱이 조용히 파손, 추적 불가). 같은 MySQL 인스턴스를 쓰되 다음을 지킨다.

1. **스키마 분리 + 읽기 전용 계정**
   같은 인스턴스 안에서 스키마(database)를 `erp` / `tax_invoice`로 분리한다. 세금계산서 앱의 DB 계정은 `tax_invoice`에 전권, `erp`의 필요 테이블(거래처 · 사업자 정보 · 매출/수주)에는 **SELECT만** 부여한다. MySQL 권한으로 강제되므로 실수로 ERP 테이블을 건드리는 사고가 원천 차단된다.

2. **발행 데이터는 단일 기록자(Single Writer)**
   발행 이력 · 5대 날짜 · 승인번호 등 비가역 데이터는 세금계산서 앱만 쓴다. 쓰는 주체가 하나여야 정합성 논쟁이 생기지 않는다.

3. **외부 발행 트리거는 테이블이 아니라 API로**
   자동화 담당이 발행을 트리거해야 하면 테이블 직접 INSERT가 아니라 세금계산서 앱이 여는 내부 API 엔드포인트로 받는다. 검증 · 멱등 처리를 통과한 단일 경로로만 발행이 일어나게 한다.

마이그레이션도 같은 원칙: 각자 자기 스키마의 마이그레이션만 소유하고, ERP 스키마 변경 중 세금계산서가 읽는 테이블은 사전 공유하는 팀 규칙만 둔다. 같은 인스턴스이므로 백업은 한 번에 커버된다.

### 2-3. 실무 체크 2가지

- **인증(SSO)**: 로그인을 두 번 시킬 수 없으므로, 세션 쿠키를 상위 도메인(`.회사도메인.com`)에 심어 두 서브도메인이 공유하거나, ERP 세션/토큰을 검증하는 미들웨어를 세금계산서 앱에 얹는다.
- **UX**: ERP 사이드바에 메뉴 링크만 걸면 사용자는 한 시스템처럼 쓴다.

### 2-4. "나중에 합쳐질 것"에 대한 관점

합치는 전제여도 지금 분리는 손해가 아니다. 핵심 자산이 헤드리스 훅 + 순수 함수로 이미 분리돼 있어, 통합 작업은 "서브도메인2 앱을 폐기하고 `modules/tax-invoice` 폴더를 ERP 저장소로 옮겨 그리드에 붙이는 것"이라 비용이 작다. 반대로 지금 무리해서 한 저장소에 합류하면 3인이 매일 충돌 비용을 낸다. 합치지 않고 별도 서비스로 유지하는 것도 유효한 최종 형태이며, 운영해보고 결정해도 된다.

## 3. 볼타(Bolta) 연동 — 현재 코드는 100% 목(Mock)이며 실스펙과 불일치

### 3-1. 핵심 진단

현재 `boltaApiClient.ts`는 실제 네트워크 호출이 없는 목이고, **실제 볼타 API 스펙과 구조적으로 다르다.** LLM(Gemini)이 공식 문서 없이 스펙을 창작한 결과물이므로 필드명 · 흐름을 신뢰하면 안 된다.

### 3-2. 실스펙과의 차이 (docs.bolta.io 기준, 2026-08 확인)

| 항목 | 현재 코드 | 실제 볼타 API |
|---|---|---|
| 엔드포인트 | `api.bolta.io/v1` (호출 없음) | `xapi.bolta.io/v1/taxInvoices/issue` |
| 인증 | apiKey 필드만 존재 | API 키 Basic 인증 (`test_` / 라이브 키 분리) |
| 당사자 필드 | `supplier.regNo`, `buyer` | `supplier` / `supplied`의 `identificationNumber`, `organizationName`, `representativeName`, `manager(s)` |
| 품목 필드 | `supplyAmount`, `taxAmount` | `supplyCost`, `tax` |
| 영수/청구 | 없음 | `purpose`(RECEIPT/CLAIM) 필수 |
| 발행 흐름 | 동기 — 승인번호 즉시 반환 | **비동기** — `issuanceKey` 반환 후 웹훅/조회 API로 완료 확인 |
| 수정발행 | 사유코드 '1'~'6' 단일 필드 | 사유별 별도 엔드포인트 (계약해제는 `date`만 전달, 이중발급은 본문 없음, 원본 품목 음수면 수정발행 불가 등) |
| 발급자 개념 | 없음 | 발급자 등록 → `issuerId` → 인증서 등록 URL 발급 흐름 존재 |

비동기 + 웹훅 구조이므로, 서브도메인2 백엔드에는 **웹훅 수신 엔드포인트 + 발행 상태 머신**이 필요하다(현재의 `InvoiceStatus`를 볼타 웹훅 이벤트와 매핑).

### 3-3. 공동인증서 / 가입 요건

알고 있는 내용이 맞다. 실제 온보딩 플로우:

1. 회원가입 · 워크스페이스 생성
2. 개발자센터에서 **테스트 API 키**(`test_` 접두사) 발급
3. 발급자 등록 API → `issuerId` 획득
4. 인증서 등록 URL 조회 API → 해당 URL에서 **공동인증서 등록**
5. 라이브 키 사용 시 사전 **포인트 충전** 필요 (잔액 부족 시 호출 실패)

단, **테스트 환경에서는 테스트 인증서를 제공**하므로 실제 공동인증서 없이 연동 개발이 가능하고, `test_` 키 호출은 포인트 없이 무료로 가상 처리된다. 즉 공식 신청 · 실인증서 등록은 라이브 전환 시점의 문제이며, 회원가입만 하면 지금 바로 실스펙 개발을 시작할 수 있다.

### 3-4. 권장 작업 순서

1. 목 클라이언트는 수리하지 말고 **폐기**한다.
2. 볼타 공개 **OpenAPI 스펙(`docs.bolta.io/openapi.yaml`)**을 받아 `openapi-typescript` 등으로 타입을 생성한다 — 필드명 불일치를 원천 해결.
3. 기존 자산(5대 날짜, 이상탐지, MOD-10) ↔ 볼타 스키마 간 **매핑 레이어**를 새로 작성한다.
4. 볼타 회원가입 후 테스트 키 + 테스트 인증서로 정발행 → 웹훅 수신 → 조회까지 E2E 테스트.
5. 수정발행은 사유별 엔드포인트 기준으로 재설계 (특히 음수 금액 제약 반영 — §1-2 ③의 절사 버그와 연결됨).
6. 교훈: LLM에게 외부 API 연동을 시킬 때는 반드시 공식 문서를 컨텍스트로 제공할 것. 문서 없이 시키면 스펙을 창작한다.
